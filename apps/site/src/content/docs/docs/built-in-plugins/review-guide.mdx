The Review guide plugin walks you through a task's pull request. The agent harness you pick, such as
Claude Code or Codex, reads the change in the task's worktree and arranges its hunks into steps in the
order you'd read them, starting where the data or the request comes in. Core changes come first, and
tests, docs, and wiring come after. Each step explains what its part of the change does and why,
then shows its hunks with a few short notes on the lines worth a closer look.

<PluginFacts id="review-guide">
  <Fragment slot="adds">The **Guide** pane on a task, a **Guide** tab in a task's pull request or merge request view, its notes under their lines in the **Diff** tab, and the **Open review guide** command.</Fragment>
  <Fragment slot="needs">A task with a pull request on GitHub, a merge request on GitLab, or a pull request on Bitbucket, and Claude Code or Codex installed.</Fragment>
</PluginFacts>

## Write a guide

<Steps>

1. Open a task that has a pull request or merge request. In its **Pull request** or **Merge request** pane, click the **Guide** tab, or open the **Guide** pane.

2. Click **Generate guide** at the top of the guide. In the dialog, add any extra context, such as what
   to focus on or who's reviewing. To change the harness or its model, click ✦. Then click **Generate**.

   <Checkpoint>The guide says the harness is writing it, with a link to its session. When it finishes, the guide opens on its overview.</Checkpoint>

</Steps>

The harness runs one turn in an agent session of the task, so a guide spends that harness's usage. The
turn can read the worktree but can't change it. **Stop** ends the turn. The extra context goes to the
harness with that turn only. acorn doesn't keep it with the guide.

## Write a guide from a workflow

Add a **Generate a review guide** step, `review-guide:generate`, to a workflow you start, such as one
that reviews a pull request. When the run reaches the step, it writes the task's guide the same way the
pane does and waits until it's done, so the guide is ready in the **Guide** tab when you open the pull
request.

```toml
[[steps]]
name = "guide"
kind = "review-guide:generate"

[steps.with]
background = "${steps.implement.output}"
```

- **Harness** is optional. Leave it empty to use the harness you picked in the pane.
- **Background** is optional. Give it what an earlier step said about the change, such as the plan or
  the report from the step that wrote the code, so the guide can explain why the change exists. The
  harness trusts the diff where the two disagree. Only the first 32,000 characters go to the harness.
- If a guide is already being written for the task, the step waits for that one. That guide doesn't
  get this step's **Background**.
- A later step can read the summary and the step titles as `${steps.guide.output}`.
- The turn's cost counts toward the run's `max_cost_usd`.
- When the guide fails, or you stop the run, the step fails with the same message the pane shows.

## Walk the path

A guide is a path: an overview, one page per step, and a wrap-up. In the **Guide** pane a rail on the
left lists every page with your progress. Each step's row shows its kind, its hunks, a rough number of
minutes, and a dot for each note in its tone, so you can see where the risk is before you start. In
the **Guide** tab beside the diff, numbered buttons along the top take its place.

- **The overview** has a summary of the whole change, which harness wrote it for which commit, the
  counts, and a card for each step. Click **Start the path**.
- **Each step** explains what its part of the change does and why, then shows its hunks. Click **Mark reviewed & continue** when you're done with it, or **Back** to go back.
  A binary file, a rename, or a mode change shows its path and what changed.
- **The wrap-up** lists every **Look closely** and **Risk** note as a checkbox, with a link to its step.
  Check each one once you've made up your mind, then leave your review in the pull request's
  **Details**. The guide never approves or comments for you.

The guide remembers which steps you marked and which notes you checked, and the pane and the tab
beside the diff show the same progress. When you come back to the guide, it opens on the page you had
open, scrolled where you left it, and a guide you open fresh starts on the first page you haven't
reviewed. **Regenerate** opens the same dialog and starts a new guide with no progress. In the tab beside the diff, a step shows only its noted lines, and opening it
scrolls the diff next to it to the step's first hunk.

Under a line is any note the harness pinned to it. Each has a tone, **Explains** for context, **Look
closely** for a judgment call, or **Risk** for a likely bug, then a title and a short body. Click
**Mark checked** on a note you've settled, or **Got it** to fold an Explains note. Most hunks have
none.

Above each hunk is a link with its file and first line, such as `src/billing/invoice.ts:42`. Click it,
or a note's **Show in diff**, to open the pull request's diff at that line, where you can see the code
around it and comment. Hunks the harness left out are a last step, **Not covered by the guide**.

To ask about a note, type in the reply box under it. The note is the first message of the line's
conversation with an agent, so the agent gets the note's text with your first question, and your
question can be short. To ask about any other line, click ✦ beside it. The agent card opens right there,
in the guide. It's the same conversation as on that line in the pull request's **Diff** tab, so you can
carry on in either place. Nothing goes to the agent until you send.

acorn checks the harness's answer against the diff before it shows it. Every hunk appears exactly once:
a hunk the harness left out goes to **Not covered by the guide**, a hunk it put in two steps stays in
the first, and an ID that isn't in the change is dropped. The pane says when it moved or dropped
anything, so a guide can arrange the change but can't hide any of it.

Each note quotes the text of the line it's on, and acorn checks the quote against the diff too. A note
with the wrong line number moves to the one line that has its text. A note whose text matches no line,
or more than one, is dropped, and so is any past three on a hunk or 40 in a guide. The pane says how many
it dropped, so a note never sits on a line it doesn't describe.

## In the Diff tab

You don't have to open the guide to see what it flagged. Each note also shows under its line in the
pull request's own **Diff** tab, as the same agent card with the note's title and body and a reply box
under it. A reply there is the conversation the guide shows on that line. The notes only show while the
guide is up to date and its commit is the pull request's latest, so they never sit on lines that moved.
Until then, the guide's notes have no reply box, and ✦ opens the line in the pull request's diff. A note
in the Diff tab doesn't open its step.

## When the change moves on

A new commit on the task marks the guide out of date, and the pane says the change has new commits.
When the guide and the pull request are on different commits, the pane names both. Until they match, you
can't ask about a line in the guide and the **Diff** tab doesn't show its notes. Push the branch if it has
commits the pull request doesn't, or click **Regenerate** if the pull request moved on.
acorn doesn't write a new guide on its own, because each one spends usage. Click **Regenerate** when you
want one.

## What it can reach

It reads the task's pull request from its code host plugin, and the change from the task's worktree with
git. It has no network access of its own, runs no other programs, and reads no secrets. It may open the
task's pull request diff at a line, which is what a hunk's link does, and show the agent card on the
pull request's lines in the guide. The card waits for you to send a question. The guide is
kept on the Node until the task is deleted.

The **Guide** tab sits beside the diff, so you can read a step and its code in the diff side by side.

## In the terminal

The terminal client draws the same pane and the same tab, with no agent card. A note is one line with
its tone and title, then its body, and Enter on that line folds it. A hunk's link, or Enter on a line of
the diff, opens the file in the **Editor** pane at that line, rather than in the diff. To ask about a
line there, use the Agent pane.

## Limits

- A guide covers the task's own pull request, not a related one.
- A change larger than 16 MB can't have a guide.
- The guide covers the worktree's latest commit, which can be ahead of the pull request when a commit
  hasn't been pushed. A hunk's link then lands on its file's header when the pull request's diff doesn't
  have the line, and the **Diff** tab shows none of its notes until you push.
