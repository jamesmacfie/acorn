# Herdr top-100 compatibility matrix

Status: Normative compatibility assessment; external repository facts are informative snapshots<br>
Requirement prefix: `HERDR`

This appendix tests the Acorn V2 plugin model against a concrete external corpus. It does not bless,
install, or redistribute any listed software. “Supported” means the observed behavior has a safe
representation in the specified Acorn contracts; it does not mean the existing Herdr artifact can
run unchanged or that Acorn has verified its publisher.

The normative [contract archetypes and expansion ledger](./herdr-contract-archetypes.md) supplies
the complete operation, event, worker, storage, renderer, lifecycle and build semantics for every
row and is part of the Supported assertion. The machine-expanded
[`herdr-top-100-fixtures.json`](../contracts/examples/herdr-top-100-fixtures.json) preserves every
observed surface occurrence, validates each installable port manifest and records explicit
Extension/Unsupported activation decisions.

## Snapshot and method

- **HERDR-METHOD-001:** The source is the
  [Herdr plugin marketplace](https://herdr.dev/plugins/), accessed 2026-07-30. Its downloaded JSON
  fixture was generated `2026-07-30T10:30:55.700Z` from the public GitHub topic query
  `topic:herdr-plugin is:public`.
  Its `plugins` array contains 416 records, while its `source` block reports `totalCount: 421`,
  `collectedCount: 421` and `truncated: false`. This review sorts the 416 records actually present,
  records the fixture’s internal count discrepancy, and does not invent the five absent records.
- **HERDR-METHOD-002:** Repositories were sorted by snapshot stars descending and then `pushedAt`
  descending; exactly the first 100 form this matrix. Stars and language below are fixture values,
  not live counters.
- **HERDR-METHOD-003:** On 2026-07-30 each repository’s current default-branch `HEAD` was resolved
  with the Git protocol, its exact commit archive was acquired, and all 100 archives were read. The
  review parsed every `herdr-plugin.toml`, resolved literal manifest entrypoints where present, and
  inspected README, source and package/build files. In total it read 101 manifests, 332 directly
  resolvable manifest command files and 4,520 source/package files. A linked commit and source tree
  make each observation reproducible.
- **HERDR-METHOD-004:** Runtime and trust are target Acorn classifications. `Community` executable
  logic means a WASI port; retaining a native executable requires Acorn Verified provenance and the
  real OS sandbox. No row grants in-process system status.
- **HERDR-METHOD-005:** Descriptions are concise behavior syntheses checked against manifest and
  source. They are not copied documentation contracts. Manifest absence, fixtures and duplicate
  declarations are called out rather than inferred away.

## Reading the matrix

Herdr surface shorthand is exhaustive by surface kind: `A` action IDs, `P` pane IDs, `E` subscribed
event types, `S` startup entries, `L` link handlers, `B` build entries and `W` a source-observed
long-running worker/daemon. Counts are per repository after de-duplicating repeated IDs/types;
aggregate entry counts below preserve repetitions. `—` means absent at the inspected commit.

Acorn permission names abbreviate the normative `core.workspace`, `core.repository`, `core.task`,
`core.file`, `core.git`, `core.process`, `core.terminal`, `core.agent`, `core.network`, `core.secret`,
`core.events`, `core.plugin`, `core.ui`, `core.clipboard`, `core.notification`, `core.storage` and
`core.provider` families. Every row’s listed authority remains constrained by Node, installation,
caller delegation and target resource; “secret use” always means brokered opaque references.

### Shared lifecycle, fallback and observability answers

The rows inherit these answers unless their Fit cell names a stricter extension or decision:

- **HERDR-LIFECYCLE-001:** Every representable artifact follows the coordinated, resumable
  Node/client acquisition transaction, immutable verification, permission review, setup gate,
  staged activation and health check in the plugin lifecycle specification. A Herdr `build` entry
  becomes registry build provenance or an isolated credential-free source build; it is never an
  Acorn install script.
- **HERDR-LIFECYCLE-002:** A row with `W` names a separately supervised worker. Update drains it,
  revokes old-generation handles and switches only after new-generation readiness. Crash loops,
  sandbox violations or invalid event behavior degrade and then quarantine the installation.
  Startup entries reconcile desired durable state after restart; they are not arbitrary shell
  startup authority.
- **HERDR-LIFECYCLE-003:** Every row naming own durable state uses only that installation’s SQLite
  database/blob allocation and signed migrations. Update takes a recoverable migration backup.
  Uninstall offers immediate deletion or disclosed encrypted retained data; reinstall reclaims data
  only when plugin/publisher identity and schema compatibility match. “Own config only” follows the
  same retention decision; “no state” leaves no plugin data.
- **HERDR-LIFECYCLE-004:** Revocation immediately invalidates secret, network, process, terminal,
  provider, browser and collaboration handles. Disablement stops new work and drains safe
  in-flight work; rollback never restores a revoked grant or older vulnerable artifact.
- **HERDR-FALLBACK-001:** Declarative views use standard loading, empty, stale,
  permission-denied, unsupported and error states. Native terminal tools fall back to status,
  bounded logs and manual external instructions. Browser or bespoke views provide a semantic
  fallback. Future mobile clients show compact status/actions when capable and an explicit
  desktop-required state otherwise; no UI absence grants or disables Node authority.
- **HERDR-O11Y-001:** Every command, worker, high-risk capability use, credential use, lifecycle
  transition, replay gap and quarantine emits privacy-safe structured health/audit data. Source
  content, terminal transcripts, prompts, provider bodies, absolute paths and secret values are
  excluded by default. Each row’s declared worker, stream and dependency is therefore observable
  without granting telemetry egress.

### Named extensions and decisions

| ID | Disposition |
| --- | --- |
| `HERDR-EXT-001` | Implement the already-constrained opaque relay transport, push delivery and a mobile client. It is not a V2 deliverable. |
| `HERDR-EXT-002` | Publish the task-scoped browser-control capability, action/snapshot schemas and Electron driver host anticipated by `UI-MEDIA-020`; preview alone is insufficient. |
| `HERDR-EXT-003` | Add a host-owned, template-only Electron window-title contribution with bounded fields, accessibility fallback and no raw terminal escape sequences. |
| `HERDR-EXT-004` | Add an audited provider request/response transform chain with ordering, fail-open/closed policy, byte ceilings and redacted usage accounting; it never exposes provider credentials. |
| `HERDR-DEC-001` | Installation, updates, enablement and removal stay in the core marketplace. A plugin may deep-link to that UI but cannot become an installer. |
| `HERDR-DEC-002` | Acorn does not create SSH “shadow” workspaces that impersonate remote resources; clients pair directly with the owning Node and preserve canonical identity. |
| `HERDR-DEC-003` | A links directory is marketplace/catalog input, not an executable or declarative plugin installation. |

## Aggregate evidence

- **HERDR-AGG-001:** All 100 repositories resolved and were inspected. Ninety-nine contain a
  product manifest; `MIDO-ruby7/herdr-plugins-directory` contains none. There are 101 manifests
  total because `dcolinmorgan/herdr-remote` has two product copies and `caioniehues/herdmates`
  includes a test-fixture manifest in addition to its product manifest.
- **HERDR-AGG-002:** At repository level, 90 declare actions, 66 panes, 41 events, 53 builds, eight
  link handlers, six startup hooks, four legacy `keys` blocks, one `keybindings` block and one
  theme. Across all 101 files there are 294 action entries, 108 pane entries, 130 event entries, 59
  build entries, ten link-handler entries and seven startup entries.
- **HERDR-AGG-003:** Event pressure concentrates on `pane.agent_status_changed` (22 entries),
  `workspace.created` (12), `worktree.created` (11), `pane.focused` (11),
  `workspace.focused` (10) and `pane.agent_detected` (10). Pane placements are 47 overlay, 31 split,
  ten zoomed, nine popup, eight tab and three unspecified entries.
- **HERDR-AGG-004:** The Acorn assessment is 89 Supported, seven Extension and four Unsupported.
  Unsupported means an explicit product decision, not a missing analysis.

## Limitations and interpretation

- **HERDR-LIMIT-001:** This is a point-in-time source review. A repository can change after its linked
  commit; star counts, default branches, marketplace membership and upstream security posture are
  not durable product facts.
- **HERDR-LIMIT-002:** Source inspection establishes requested behavior, not safety. No artifact was
  executed, no publisher identity was verified, no SBOM/provenance was accepted and no native
  sandbox conformance was performed. Therefore “Verified required” is a gate, not an award.
- **HERDR-LIMIT-003:** Herdr manifests describe commands and hooks but not Acorn-grade authorization,
  idempotency, transactional outboxes, replay, delegated authority, data classification or fallback.
  The Acorn mapping supplies those constraints; it does not claim wire compatibility.
- **HERDR-LIMIT-004:** Build entries are evidence of source-build needs, not permission for install
  scripts. Acorn would consume immutable signed artifacts or run credential-free isolated builds.
- **HERDR-LIMIT-005:** Existing tools that read home-directory tokens, agent databases, sockets,
  shell environments or arbitrary config must be redesigned around brokered secrets, profile
  exports, rooted resources and fixed-tool calls. Developer Source may retain unrestricted behavior
  only with its permanent unrestricted-code warning.
