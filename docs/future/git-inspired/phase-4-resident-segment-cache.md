# Phase 4: a bounded resident cache for recent diff segments

Status: shipped 2026-09-26, tested in unit and jsdom suites. The real-window warm-revisit run is owed.

## Goal

Returning to a recently viewed diff can paint its last visible plain rows immediately and reuse their
syntax and word enrichment. The cache remains inside one renderer's node partition, is bounded by
rows and estimated bytes, evicts at segment granularity, and never persists parsed content or DOM.

## Why this phase

Acorn already retains provider query data and raw Node-side blobs, but parsed rows and tokens belong
to a `DiffPane` mount. Reopening a complete diff can therefore show cached metadata around an empty
body while repeating work it finished moments earlier.

Caching the current monolithic `ParsedFile[]` would retain the architecture phase 2 removes and make
large files the indivisible eviction unit. Segments provide bounded entries, stable content keys, and
a natural visible-working-set pin.

## Scope

In:

- One `DiffSegmentCache` per renderer node partition.
- Immutable plain segment payloads and optional enrichment entries.
- A weighted LRU with independent row and estimated-byte ceilings.
- Visible, near-visible, and in-flight pins; deterministic handling of one oversize segment.
- Source-defined cache namespaces that allow the same PR revision to be shared between task and
  repository views without sharing across nodes or unrelated sources.
- Superseded working-tree content eviction.
- Hit, miss, insert, promotion, eviction, oversize, resident-row, and resident-byte probes.
- Cache lifecycle integration with node removal, renderer teardown, document revision, and phase 2
  loaders.

Out:

- IndexedDB or filesystem persistence.
- Cached DOM, Solid owners/signals, composers, drafts, `HTMLElement`s, observers, or in-flight
  promises after their caller releases them.
- An item-count-only “last N diffs” policy. Documents vary too much in size for count to be the
  primary bound.
- Treating provider query cache and parsed segment cache as one store.
- Keeping every working-tree revision generated by the ten-second Changes poll.

## Ownership and partitioning

The cache has the same security and lifecycle partition as the renderer's QueryClient: one active
node, one in-memory cache. The preferred integration is to add it to the object returned by
`clientFor(nodeId)` or to a neighboring per-node resource owner constructed and destroyed with that
object. Do not add `nodeId` to every entry while keeping one global store.

`dropNode(nodeId)` clears the query client, persisted query snapshot, and segment cache together.
Switching active nodes swaps cache owners. Ordinary pane unmount does not clear the node cache.

Origin-only development gets the existing `ORIGIN_NODE_ID` partition. TUI may install its own
bounded instance if it adopts the segmented document; it does not share renderer memory with the
desktop.

## Keys

The source adds a stable `cacheNamespace` to its document identity. Examples:

- GitHub PR: provider owner/repository/pull number plus the mirrored diff revision,
- GitHub compare: owner/repository/base/head revision,
- Changes: task/worktree identity plus the status/document revision.

The node partition already supplies the authority boundary. Do not include a route or pane key when
that would prevent task PR and repository PR views from reusing identical code content.

An entry key contains:

```text
cache namespace
+ document revision
+ segment id
+ segment content key
+ diff-document schema/parser version
+ enrichment version when applicable
```

Projection does not belong in the plain-payload key when unified and split use the same rows.
Projection-specific derived bands may be cached only if measurement shows that their bounded rebuild
is material, and then projection is explicit in that derived key.

Syntax tokens currently carry both light and dark colors, so theme does not invalidate them. Recheck
that contract before leaving theme out. A tokenizer grammar/version change must change enrichment
version. Comment and thread state never changes a code segment key.

## Entry types

Keep plain and enriched data separable:

```ts
type ResidentDiffSegment = {
  key: DiffSegmentCacheKey
  plain: DiffSegmentPayload
  enrichment?: DiffSegmentEnrichment
  weight: { rows: number; bytes: number }
}
```

Enrichment references rows by stable local identity and contains only token/word data. It does not
copy the plain row text unless the worker result requires it. A plain hit can paint immediately even
when enrichment was evicted or has a newer version.

Phase 3 measured block heights remain a separate entry class because their validity includes
fingerprint, layout revision, width bucket, and projection. If retained across pane unmount, they use
their own small byte/count budget and never keep block bodies or local drafts. The segment budget may
not be consumed by hundreds of stale width buckets.

## Weight and eviction

Estimate entry bytes deterministically from data Acorn already owns:

- UTF-8 byte length of raw row text and structural strings,
- token content and color strings not shared with the plain row,
- word-span payload,
- a documented fixed overhead per row, token, array, and object.

This is a budget estimator, not a claim of exact JavaScript heap size. Calibrate its constants against
phase 0 heap samples and keep the estimator pure and tested. Every entry also counts its rows, so an
underestimated object overhead cannot make the row count unbounded.

Choose the two ceilings from phase 0 warm/cold measurements and device targets. Name them and report
them in the health snapshot. The eviction rules are:

1. Visible segments are pinned.
2. In-flight consumers hold a temporary pin until success, failure, or abort cleanup.
3. Near-range segments may be pinned only while they remain in the active prefetch range.
4. Insert or promote on successful validated data, never on a stale generation.
5. Evict least-recently used unpinned segments until both row and byte budgets pass.
6. If one visible segment exceeds a ceiling, keep it as the sole oversize resident while pinned,
   record the condition, and evict it immediately after its last pin. Do not split it differently in
   the cache from the topology that addresses it.
7. An enrichment insert may evict older enrichment before evicting the same segment's plain payload,
   because plain rows are the first-content path.

The outcome should usually resemble “the last few diffs,” but the contract is weighted memory, not a
document count.

## Revision and source lifecycle

- An immutable PR or compare revision can remain until LRU eviction.
- A force-pushed PR receives a new document revision and cannot hit old segment keys.
- A working-tree content-key change immediately removes superseded entries for that namespace/file;
  the ten-second poll must not leave a trail of edits under the global budget.
- A no-op Changes poll retains entries because its content keys do not move.
- A thread resolve/body change leaves code segments intact and invalidates only matching height or
  block-content data.
- Removing a project/task may purge its Changes namespace when the owning runtime already emits a
  lifecycle event. Do not add a fan-out solely for cache neatness if the weighted LRU already bounds
  it.
- Node removal and renderer teardown clear all entries and pins synchronously; storage cleanup may
  remain asynchronous as it is for the query cache.

## Loader integration

The phase 2 loader checks, in order:

1. an active local payload already published by the current pane,
2. the node's resident segment cache,
3. the source's route/query cache,
4. a network request.

A cache hit still validates schema version, content key, and document revision before publish. It
publishes plain rows in the current turn, then schedules any cached enrichment without blocking
paint. It promotes the LRU once per access burst, not once per rendered row.

When the Node/query cache background refresh discovers a new document revision, old cache entries do
not mutate. The source swaps topology, the loader aborts the old generation, and the LRU eventually
evicts or explicitly supersedes old entries.

Do not put segment payloads into the persisted QueryClient snapshot. The current persistence rule
already excludes patch-bearing file queries; add the new query-key family to that exclusion and test
it.

## Telemetry and diagnostics

Use fixed operation labels and numeric samples:

- `diff.segment_cache.hit`, `miss`, `insert`, `evict`, `oversize`,
- resident documents, segments, rows, plain bytes, enrichment bytes,
- evicted rows/bytes and reason (`budget`, `superseded`, `node-drop`, `teardown`),
- time from pane mount to first plain segment, with cache outcome as a fixed enum.

No cache namespace, segment key, path, revision, source text, or search query enters telemetry. The
phase 0 exact local health snapshot may expose counts and weights only.

## Tests

- LRU order: hit promotes; insertion evicts the oldest unpinned entries until both budgets pass.
- Dual budget: rows can trigger eviction below the byte ceiling and bytes can trigger it below the
  row ceiling.
- Pins: visible and in-flight entries survive pressure; every success, error, abort, revision swap,
  and unmount releases its pins.
- Oversize: one visible oversize entry is usable, becomes the sole resident, and leaves on unpin.
- Plain/enrichment priority: enrichment pressure drops enrichment before the only warm plain segment
  needed for first content.
- Keys: same head blob with a different patch, parser version, or content key misses; theme changes
  hit while the dual-theme token contract holds; thread state changes hit code and miss only height
  data.
- Changes churn: repeated no-op polls retain entries; one file edit evicts only superseded content
  for that file/namespace.
- Partitions: identical keys on two nodes do not share; `dropNode` clears exactly one cache.
- Persistence: dehydration contains no plain segment, tokens, patch text, or height measurements.
- Privacy: canary paths/text do not appear in metrics or serialized health snapshots.
- Real-window flow: a warm revisit records a hit and paints cached plain rows before a segment
  request; cycling through documents keeps resident weight under both ceilings.

## Done when

- Returning to the most recently viewed canonical diff paints its last visible plain segment from
  memory without reparsing or waiting for the Node.
- Cycling through more documents than fit evicts deterministically and never exceeds the configured
  row or byte ceiling except for the one documented visible-oversize case.
- A working-tree edit, force push, parser change, and node switch cannot reuse stale content.
- Query persistence contains no parsed rows or tokens.
- `pnpm lint`, cache and persistence suites, provider/client diff suites, the canonical warm-revisit
  flow, and `pnpm test` pass.

Where the pieces live, for phase 5:

- The cache is `packages/client-core/src/features/diff/segmentCache.ts`: `createSegmentCache`,
  `segmentCacheFor(queryClient)`, `dropSegmentCache`, `residentKey`, `plainWeight`, and
  `enrichmentWeight`. `peek`, `has`, and `insert` are the read and write paths. `holder()` returns a
  claim that `hold`s a key set, `release`s it, and `supersede`s a patch.
- The loader is `features/diff/segmentLoader.ts`. It takes the cache as `cache`, and `rows`,
  `status`, and `retry` take a segment address (content key, path, and sha) instead of a content key.

Deviations from the plan:

1. **Keyed by the query client, not added to `clientFor`.** `segmentCacheFor` keeps one cache per
   `QueryClient` in a `WeakMap`, and `DiffPane` finds its cache from `useQueryClient()`. The pane
   reads the partition it already draws from, with no second lookup through `activeCacheId()` that
   could disagree with the provider during a switch. `dropNode` calls `dropSegmentCache`. A test's
   own client gets its own cache, so the suites stay isolated without a reset hook.
2. **No `cacheNamespace` and no document revision in the key.** A segment's content key is already
   the patch digest, the diff-document version, and the ordinal. The rows built from it depend only
   on that, the path, and the sha, so `residentKey` is those three strings. Any source on the node
   that names the same key names the same rows, and a force push or a working-tree edit has new
   digests. None of the three sources changed. The path and sha are in the key because the old
   per-pane map keyed by content key alone would give two files with the same patch one set of rows.
3. **No enrichment version and no parser version beyond the content key's.** The renderer's
   tokenizer and row builder cannot change within a process, and nothing is persisted, so a new
   build starts with an empty cache. Tokens carry both themes' colours, so theme is not in the key
   either.
4. **Superseding is the pane's, and keyed on the file set.** A source has no namespace to supersede
   in. The pane drops a file's old patch when its revision moves and its signature does not, which is
   exactly a working tree saving under the reader. A pull request's next commit changes the signature,
   so its old revision stays for the budget, as the plan asked. Task and project removal add nothing:
   the budget bounds a removed task's entries.
5. **Pins are claims, one per pane.** A pane's claim is its visible and near segments plus whatever
   it is loading or colouring, replaced on every range change. The near range is the demand's two
   segments either side, so a near pin ends when the range moves. A new revision keeps the old claim
   until the next demand, so rows that survive the revision are not evicted in between. The loader has
   no path that leaves a claim behind: success, failure, and abort all end in the request's `finally`,
   and `reset` and `dispose` rebuild or release it.
6. **Eviction drops colour and then rows, per segment, oldest first.** The plan's rule 7 is met at
   each segment: its colour goes before its plain rows. The cache does not strip colour from every
   segment before evicting any plain rows, which would leave the most recent diff grey to keep the
   oldest one's rows.
7. **Oversize is counted per insert.** A batch that leaves the cache over a ceiling with nothing
   unheld counts once. The held segments stay, and the next change to any claim evicts them if nothing
   holds them.
8. **Heights are not retained.** They stay per pane, as phase 3 left them. A revisit draws its rows
   from memory and measures its blocks again on mount.
9. **No query-key exclusion.** Segments never pass through the query cache, so there is no key family
   to exclude. The persistence test dehydrates a client after a diff loaded and finds no segment text.
10. **The byte estimate counts UTF-16.** Text is two bytes a character, which is closer to the
    engine's own strings than UTF-8 bytes would be. The allowances are 64 bytes a row, 16 an array,
    and 48 a token.
11. **Ceilings chosen by hand.** 40,000 rows and 32 MiB. No heap sample or first-content timing
    could be taken, because the worktree's window runs hidden behind the developer's own app.
12. **Health.** The `resident` group gained `plainBytes`, `enrichmentBytes`, `hits`, `misses`,
    `inserts`, `evictions`, `oversize`, `rowCeiling`, and `byteCeiling`, and it reports the node's
    cache rather than the pane's rows. `documents` counts distinct patches held. `hits` and `misses`
    are the pane's since mount; the rest are the cache's. `SegmentStatus` lost `loaded`, because the
    cache is what says a segment is loaded.
13. **The terminal client has no resident cache.** Its diff pane has its own loader, and it does not
    share renderer memory with the desktop.

Not built or not verified:

- The real-window flow: a warm revisit painting before a request, and resident weight staying under
  both ceilings while cycling documents. Smoke item 84 in [testing.md](../../testing.md) is owed.
- The estimator's calibration against a heap sample, and the phase 0 before and after measurements.
- A colouring that fell back to plain text after a worker timeout is cached as that segment's colour
  until it is evicted. `enrichDiffRows` does not say when it fell back.
