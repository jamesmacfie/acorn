Date: 2026-09-24. Status: proposal. [Back to the plan](./README.md).

## R1: Remove the serial hop in front of the app

**What was found.** Commit `d5ba5393` made `apps/desktop/src/client/bootstrap.ts` the page entry. It
installs error listeners that draw a readable failure screen, then runs `import('./index.tsx')`. Two
costs follow:

- **A serial hop.** Nothing else starts downloading until the bootstrap chunk has been fetched,
  parsed, and run. Before, the HTML named every startup chunk as a `modulepreload` and the webview
  fetched them in parallel with the entry.
- **74 more requests.** A dynamic import boundary at the top of the graph makes the bundler keep
  modules as separate chunks instead of merging them. The same thing happened in September with a
  top-level `await`, and removing it took 91 requests off startup
  ([phase 2](../../../performance/2026-09-03--phase-2.md)). Each request goes through the Rust scheme
  handler on its own thread.

The stylesheets moved from `<link>` tags in the head to JavaScript preloads as well.

**Change.** Keep the failure screen and drop the hop. Two ways, in order of preference:

1. Make `index.tsx` the entry again, and put the failure listeners in a tiny static script served
   from `apps/desktop/public/` and named in `index.html` before the module script. A classic script
   runs before any module script evaluates. It can catch evaluation errors through `window.onerror`
   and a module fetch failure through an `error` listener on the module script element. It has to
   pass the Content-Security-Policy: `script-src 'self'` allows a same-origin file, but not an inline
   script.
2. If that does not catch every failure the bootstrap catches, keep the bootstrap and add
   `modulepreload` links for its dependency list with a small Vite plugin, so the fetches start
   with the page again. This keeps the extra chunks.

**Done when.** The startup set is back to about 120 requests or fewer, with styles as `<link>` tags,
and a deliberately broken import in a test build still shows the **Acorn could not start** screen.

## R2: Take plugin code off the startup graph

**What was found.** Every compiled plugin's client entry is imported statically by
`apps/desktop/src/client/plugins.ts`, and each entry registers its contributions at startup. That is
by design. What should not be at startup is code a contribution only needs when it draws. The source
map shows these on the startup graph:

| Module | Bytes | How it gets there |
| --- | --- | --- |
| `plugins/memory/src/client/FindingsBundleReview.tsx` | 14,047 | `MemorySection.tsx` imports it statically, and `plugins/memory/src/client/index.ts` imports `MemorySection` |
| `plugins/workflows/src/client/editor/draftStore.ts`, `draft.ts`, and `shared/stepFields.ts` | about 16,800 | `plugins/workflows/src/client/commands.ts` imports `emptyDefinition`, `defRefKey`, and `startRequest` from the editor |
| `packages/client-core/src/kit/components/content/Graph.tsx` | 5,138 | Not traced. Find the importer. |
| `packages/dashboards-core/src/chart.ts`, `shaping.ts`, and `client-core/features/dashboards/persist.ts` | about 11,800 | Not traced. Dashboards draw only on a dashboard surface. |
| `plugins/github/src/client/GithubImporter.tsx` | 3,359 | Not traced. |
| `plugins/preview/src/client/PreviewPane.tsx` | 2,329 | `plugins/preview/src/client/index.ts` imports `activatePreviewEvents` from the pane file |

**Change.** One fix per row, each in the plugin that owns it. The rule is the one
[frontend.md](../../../frontend.md) § Startup budget already states: a registration holds a loader,
not a value. In practice:

- A component used only after a click is `lazy(() => import(...))` at the registration.
- A command that needs one small helper from a heavy module gets that helper moved into a small
  module of its own. `defRefKey` and `emptyDefinition` probably do not need the whole draft store.
- A side-effect function that lives in a component file, such as `activatePreviewEvents`, moves into
  its own module.

Add the chunk names that move off startup to the denylist in
`apps/desktop/scripts/check-renderer-budget.mjs`, so they cannot come back. This depends on
[M1](./01-measurement.md#m1-make-the-renderer-startup-check-see-the-real-graph).

**Expected gain.** About 55 KB for the rows above. Measure the rest of each plugin's startup share
after these land and decide whether there is a second round.

## R3: Activate client plugins once when nothing changed

**What was found.** `apps/desktop/src/client/activate.ts` activates every compiled plugin at startup
with nothing disabled. When the node answers, `applyNodePlugins` calls `initClientPlugins` again with
the node's disabled list. `initClientPlugins` in
`packages/client-core/src/host/registries/extensionPoints/plugin.ts` disposes and re-registers every
plugin's contributions and runs every `activate` again, even when the disabled list is empty, which
is the usual case.

Three costs follow on every launch:

- Every registry notifies twice, so everything that reads the pane, source, command, and keybinding
  registries recomputes during startup.
- `activate` in `plugins/agents/src/client/index.ts` calls `activateManagedAgentNotifications()`, which
  creates a new reactive root and a new socket subscriber each time and never disposes the last one.
  Each root primes the roster with `managedAgentStore.loadAll()`, so a launch fetches every session
  twice. A node switch adds another.
- `activateManagedAgentPaneIntents()` returns a disposer that `activate` drops, so each pass adds
  another `presentation:pane-intent` listener.

**Change.** Two parts, both small:

1. In `initClientPlugins`, skip a plugin whose enabled state did not change since its last activation.
   Keep the full re-run for a plugin that was disabled and is enabled again.
2. Give `activate` the same disposable bookkeeping `init` has, and make the agents plugin return its
   disposers through it, so a pass that does re-run cannot leak.

**Done when.** A launch against a node with nothing disabled shows one `agents.roster.load` miss for
`loadAll`, not two, and a test holds that a second `initClientPlugins` call with the same disabled
list registers nothing.

## R4: Look at the two large libraries at startup

These are candidates to investigate, not changes to make:

- **`@opentui/keymap`, 79 KB.** The desktop's one keyboard engine. It is needed before the first key
  press, but not before the first frame. Check whether `installKeymap` in `client-core/host/keys` can
  load it after the shell mounts, with key presses before that point queued or dropped. Dropping a
  key press in the first 100 ms of a launch is probably acceptable. Confirm with the owner.
- **`zod`, 73 KB.** The renderer uses the protocol package's schemas. Find which of them run at
  startup. If most are types and a few are runtime checks, `zod/mini` exports a smaller tree-shakable
  API with the same schemas, but switching is a large change across `packages/protocol`, and the node
  shares those files. Do not start this without a number that says parse time matters.

## R5: Consider fewer, larger chunks

After R1 the startup set is about 120 requests. Each request is one thread and one file read in
`apps/desktop/src-tauri/src/app_scheme.rs`. The September record argued that depth matters and count
does not, and nobody measured the count's cost in WKWebView. Measure it once, in a packaged build: a
build with the startup modules grouped into a handful of chunks through the bundler's chunk-grouping
option, against the default. Adopt the grouping only if first paint moves by more than about 20 ms.
Grouping has a cost: a change to any module in a group invalidates that group's cache entry.

## Verify before building

- Rebuild and re-read the startup set. Chunk names and sizes change with every edit.
- For R1, confirm that `script-src 'self'` in the renderer policy allows a file from `public/`, and
  that a classic script in the head runs before the module graph evaluates in WKWebView.
- For R2, confirm each import chain with the source map rather than trusting the table. Some rows say
  "Not traced" because the importer was not found.
- For R3, confirm no plugin relies on `activate` running a second time after the node answers, for
  example to prime a store that needs the node's answer. If one does, give it an explicit hook for
  that instead.
