# The surfaces

Part of [docs/future/workflows/](./README.md). Status: design, 2026-09-08. Phases 3, 4, 5, and 6
build these. Every surface is drawn from the kit, so the terminal client gets it with no plugin
work; the last section says what each one looks like in cells.

## The rail source

A "Workflows" source in the left rail, `order` after Docker, glyph `workflow`, no `providerId`, so
it is present in every workspace. It declares `regions: { list, detail }` so the terminal client
puts the list in its Browse panel.

The list has two sections:

- **Definitions.** Every definition the workspace can run: database rows for this workspace, and
  every `.acorn/workflows/*.toml` in the projects the workspace holds, plus `~/.acorn/workflows`.
  Each row shows the name, a badge (`repo`, `user`, or `database`), the step count, and the project
  when the row is project-bound. A parse or cycle error is a red row with the message, as the
  palette does today.
- **Recent runs.** The last 20 runs across the workspace's tasks from `GET /v2/p/workflows/runs`,
  newest first, each with its status glyph, the task title, and how long ago. Selecting one opens
  the task with `?pane=workflows&item=<runId>`.

The list toolbar has **New workflow**. It creates a database row named "Untitled workflow" bound to
the routed project and navigates to the editor.

Selecting a definition navigates to `/p/:projectId/x/workflows/:id`, where `:id` is `db:<rowId>`,
`repo:<fileId>`, or `user:<fileId>`. The detail region, when the shell shows one beside the list,
is the read-only summary the Settings page draws today: name, posture, inputs, the node names in
graph order, problems.

```
┌ Workflows ─────────────────────────────┐
│ Definitions                    + New   │
│ ● Investigate an issue    repo · 5     │
│ ● Release notes            db · 3      │
│ ▲ nightly.toml   repo: step 'x' has…   │
│                                        │
│ Recent runs                            │
│ ◐ Investigate an issue · acorn-412 · 2m│
│ ✓ Release notes · v0.9 · 1h            │
│ ✗ Investigate an issue · acorn-401 · 3h│
└────────────────────────────────────────┘
```

## The editor surface

A `ProjectSurfaceContribution` at `/p/:projectId/x/workflows/:id`, `list-detail` layout. The
component takes `projectId` and `item`.

```

├──────────────────────────────┬─────────────────────────────────────────────────────────────────┤

│   Inputs (2)                 │                                                                  │
│                              │ Waits on   [reproduce ×] [history ×]  [+ add]                    │
│ Nodes                 + Add ▾│                                                                  │
│ ○ reproduce          agent   │ Harness    Claude Code            ▾                              │
│ ○ recent-changes   command   │ Model      claude-opus-5          ▾   Reasoning  high         ▾  │
│   └ ○ history        agent   │ Isolation  ◉ Shared task  ○ Own worktree                         │
│ ● synthesise         agent   │                                                                  │
│   └ ○ review          gate   │ Prompt                                                           │
│                              │ ┌──────────────────────────────────────────────────────────────┐ │
│                              │ │ Two investigators looked at the same issue. Write one        │ │
│                              │ │ explanation and a fix plan.                                  │ │
│                              │ └──────────────────────────────────────────────────────────────┘ │
│                              │ Insert: ${inputs.issue} ${inputs.focus} ${steps.reproduce…} …    │
│                              │ Upstream output  ◉ Append  ○ Only where referenced  ○ None       │
│                              │                                                                  │
│                              │ ▸ Result schema   ▸ Tools   ▸ Budget                             │

└─────────────────────────────────────────────────────────────────────────────────────────────────┘
```

**The list column.** One row per node, in graph order: roots first in declaration order, then each
node after the last of its predecessors, indented one level per rank. A node with two predecessors
sits under the later one and carries a `⇐ n` mark. Each row shows the name and the kind's label.
The selected row is the inspector's subject. **Add** is a menu over the catalog's kinds, grouped
built-in then by plugin, each with its icon and description. A new node is added after the selected
node with `after = [selected]`, or as a root when nothing is selected. "Definition" and "Inputs" are
rows too, so the inspector can show the definition's own fields.

**The inspector** for a node draws, in order: name (rename rewrites references; the field refuses a
duplicate or a non-slug), kind (read-only after creation; change kind is "delete and add"), `Waits
on` as removable chips with an add picker that offers every node that would not make a cycle, the
agent fields when the kind runs an agent (harness from the catalog's profiles, then each provider
config option as a select from `GET /v2/p/agents/providers`, then isolation), then the kind's
`describe.fields` in declared order, then the upstream-output toggle for agent kinds, then
disclosures for the result schema, tool ceiling, and budget. A `prompt` field has a row of insertable
chips: every declared input and every transitive predecessor. A `decide` node draws its `branches`
as verdict → node rows with an add row. A `join` node draws `joins` as a select over preceding
fan-out nodes.

The inspector for **Definition** draws name, posture, the tool ceiling, and the budget. For
**Inputs** it draws the list with name, description, required, default, and add/remove.

**The JSON tab** shows the definition as the runner's JSON (`WorkflowDef`), formatted. Apply parses
and validates; a valid document replaces the draft atomically, an invalid one keeps the last valid
draft, keeps the text for correction, and disables Save. Revert restores the last valid projection.
Positions are not in this document.

**The footer** is the validity line: valid with counts, or the first three problems from the server
validate route, each a link that selects the node it names.

**Save** is disabled while the draft is invalid or unchanged. It writes the row with the revision
it loaded; a conflict keeps the draft and shows the server's message. **Save to repo** serialises
the draft to `.acorn/workflows/<id>.toml` in the task checkout of the project's most recent task or
the project folder when none, then asks whether to keep the database row. **Run** opens the start
dialog.

**A repo or user file** opens the same surface read-only, with **Copy to database** in the toolbar
in place of Save. The list, inspector, and JSON tab all work, so a person can read a committed
workflow the same way they read their own.

**Draft rules.** These come from proliferate and are the reason the editor is pleasant to use:

- A new node starts with one edge from the selected node, or detached as a root. It is never
  inserted "between" two nodes.
- Deleting a node removes every edge touching it and never bridges its predecessor to its
  successor.
- Renaming rewrites `${steps.old.output}` in every prompt and `with` string and every `after`
  entry, in the draft only.
- Connecting refuses a self-edge, a duplicate, and any edge that closes a cycle; the picker does not
  offer those nodes.
- Backspace or Delete on the list removes the selected node after a confirm when it has edges.
  Enter never deletes.
- Undo and redo over the whole draft, typing coalesced within 600 ms, depth 60. Never while focus is
  in a text field.
- Save is disabled while the graph is invalid.

**Positions** are only relevant to the canvas (phase 6) and live in device preferences under
`plugin:workflows:layout:<defId>` as `Record<nodeName, { x, y }>`, written 400 ms after the last
move, dropped when the definition is deleted, and kept in memory for a draft that has no id yet.

## The start dialog

Opened by **Run** in the editor, by "Run a workflow" in the palette, and by the item menu. One
field per declared input in declared order, with its description as the hint and a marker on
required ones; prefilled values are editable. A task picker when the caller has no task in scope.
Confirm is disabled until required inputs are filled. When the definition declares no inputs and
the task is known, the dialog does not open and the run starts.

## The run pane

A task pane with id `workflows`, label "Workflows", glyph `workflow`, `list-detail` layout, a
per-task model, and `when: (task) => task has at least one run`. It is hidden on a task with no
runs, so the switcher does not grow a button for every task.

```
┌ Workflows ────────────────────────────┬──────────────────────────────────────────────────────┐
│ Runs                                   │ synthesise                    agent · running · $0.41 │
│ ◐ Investigate an issue     2m · $1.20 │                                                        │
│ ✓ Investigate an issue     1h · $0.98 │ Waiting on nothing. Started 40s ago.                   │
│                                        │                                                        │
│ Nodes                                  │ Claude Code · claude-opus-5 · reasoning high           │
│ ✓ reproduce         done   1m12s      │                                                        │
│ ✓ recent-changes    done      2s      │ Last said                                              │
│   └ ✓ history       done     48s      │ ┃ The regression lines up with the retry change in     │
│ ◐ synthesise     running     40s      │ ┃ pullsBatch.ts. Checking whether the cache…            │
│   └ ○ review     pending              │                                                        │
│                                        │ [Open in Agent pane]   [Kill step]                     │
│ [Cancel run]                           │                                                        │
└────────────────────────────────────────┴──────────────────────────────────────────────────────┘
```

**The list column** has the task's runs newest first (glyph, name, when, cost), then the selected
run's nodes in graph order with status, elapsed, and the same indentation the editor uses. Fan-out
children are rows under their fan-out step, as the sidebar drew them. **Cancel run** sits under the
list while the run is live.

**The detail** depends on the node's kind and status:

| Kind | While running | When done | Controls |
| --- | --- | --- | --- |
| agent | provider, model, options; last assistant text; cost so far | final text or structured JSON; cost | Open in Agent pane (`openManagedSession(taskId, step.agentSessionId)`); Kill step |
| `terminal:command` | the stdout/stderr tail, streaming | exit code, full output under a disclosure, duration | Kill step |
| `terminal:run-target` | starting… | the URL | Open terminal (`requestTerminalFocus`) |
| `database:*` | "n rows" | a table of the rows, the SQL, truncated marker | none |
| `http:request` | sending | status, headers under a disclosure, body | none |
| `gate-human` | "Waiting for you" with the run's posture | approved or rejected, by whom, when | Approve; Reject |
| `decide` | as agent | the verdict and which branch it took | as agent |
| any, `failed` or `safety-rail` | | the error | Retry; Retry with edited prompt (agent kinds, opens the prompt in a textarea) |

A step on a child task (`isolation = "worktree"` or a fan-out child) shows the child task's title as
a link that opens that task. Controls appear only when the transition is legal, so a stale button is
a race, not a bug.

**Live updates.** The pane model subscribes to `workflow:step-changed` (glyphs), `workflow:step:event`
(the selected node's tail and last text), and `plugin:workflows:run-changed` (re-read the run's
steps). On open it reads the run's steps once.

**Selection from outside.** The pane intent `{ kind: 'workflows:show-run', runId, stepId? }`, sent
by a notice target, an attention row, the rail's recent runs, and the agent pane chip. The deep link
`?pane=workflows&item=<runId>` maps to the same intent.

## The start flow from an item

The Rollbar, Linear, and GitHub row menus gain **Start workflow…** under **Create task…**. It opens
the promote-to-task modal with a workflow step on top:

```
┌ Start a workflow — RB-4412 TypeError in pullsBatch ─────────────────┐
│ Workflow   [Investigate an issue                                ▾ ]  │
│                                                                      │
│ issue *    ┌────────────────────────────────────────────────────┐    │
│            │ TypeError in pullsBatch: cannot read 'items'…       │    │
│            └────────────────────────────────────────────────────┘    │
│ focus      [                                                    ]    │
│                                                                      │
│ [ New task ]  [ Attach to task (3) ]                                 │
│ ┌──────────────────────────────────────────────────────────────────┐ │
│ │ New task in acorn.                                               │ │
│ │ Title   [Fix TypeError in pullsBatch                        ]    │ │
│ │ Branch  [james/fix-typeerror-in-pullsbatch                  ]    │ │
│ └──────────────────────────────────────────────────────────────────┘ │
│                                                Cancel   Create & run │
└──────────────────────────────────────────────────────────────────────┘
```

The workflow picker lists the workspace's definitions, filterable. Picking one draws its inputs,
prefilled by the name rule in [02-definition-model.md](./02-definition-model.md) § Inputs from the
item's title, body, and link. The two tabs are the existing ones. The primary button reads **Create
& run** or **Attach & run**. On success the modal creates or attaches, starts the run on that task
with the inputs, and navigates to `/t/<taskId>?pane=workflows&item=<runId>`. A start refusal (a
missing input the picker did not know about, a trust prompt) keeps the modal open with the message.

All three lists draw the row from `contextMenuItems('item.row', target)`, where the target is `{
location: 'item.row', id, title, providerId, projectId, body?, link? }` and a `when` may name
`providerId` and `projectId`. The existing **Create task…** row moves onto the registry too, so the
three menus cannot differ.

## The agent pane

`AgentDetailHeader` gains a chip after the title when the session's `kind` is `workflow`:
"Workflow: Investigate an issue · synthesise". Pressing it calls `openPane(taskId, 'workflows', {
kind: 'workflows:show-run', runId, stepId })`. The run and step names come from
`WORKFLOW_CONTROL.runForSession(sessionId)`, a fourth member on the capability the agents plugin
declares and workflows provides. The sidebar row for such a session shows the `workflow` glyph before
the provider glyph. The "Terminals and workflows" section is removed; `buildRoster` in
`sessions/model.ts` stops taking steps and runs.

## The palette

- **Run a workflow** (exists) searches the merged definitions for the task's workspace, not only
  the repo files, and opens the start dialog instead of starting at once.
- **Find a run** (new, `search`, task scope): the task's runs, newest first, each row naming its
  status; picking one opens the run pane. Deferred until now because there was nowhere to open one.
- **New workflow** (new, `action`, project scope): the rail toolbar's verb.
- **Approve gate** stays in the run pane, as `docs/workflows.md` § From the command palette argues.

## In a terminal

Nothing here is drawn by plugin code, so the terminal client gets each surface from the kit:

| Surface | In cells |
| --- | --- |
| Rail source | The list in the Browse panel, the summary in the main panel. |
| Editor | The `list-detail` layout: node list left, inspector right. Every field is a kit control. The JSON tab is a text area. Insert chips are buttons. |
| Start dialog | A modal with one field per input. |
| Run pane | The same layout. The stdout tail is a scrolling text region. The rows table is a `Table`. |
| Item menu | Not drawn: the terminal's descriptor source panel omits the row menu today. A door left open in phase 5. |
| Canvas | The `Graph` kit node's cell projection is the indented list the editor already draws. |
