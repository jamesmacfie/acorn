# First-party triggers, October 21, 2026

This page records the acceptance walks for the first-party suggested triggers: the ones GitHub,
GitLab, Bitbucket, Linear, Rollbar, Workflows, and Agents sources ship, and the threshold example
through `examples/plugins/acme-alerts`. [Record triggers](../workflows/triggers.md#record-triggers)
and [plugin triggers](../plugin-authoring/triggers.md) own the behavior. The walks ran on the
`phase-6-first-party-triggers` branch.

None of the four real-account walks ran. Each one needs something created on a real service, and
nobody was present to do it. The account-free walks ran in a `pnpm dev:agent` session.

## How to rerun

1. Build `acme-alerts` in a scratch folder: copy it, link `acorn-plugin-sdk`,
   `acorn-plugin-types`, and `vite` from this checkout into its `node_modules`, run
   `pnpm --filter acorn-plugin-sdk build` first, then `vite build` and `node scripts/manifest.mjs`.
   The manifest it writes matches the committed one. A reused session picks up a rebuilt copy on its
   next launch, as an update.
2. Run `pnpm dev:agent -- --session trig6` once so it stages, and stop it. Copy the plugin's
   manifest and `dist` into `apps/desktop/dist/bundled-plugins/acme-alerts`, then launch with
   `--reuse --prepared`, so staging doesn't clear the copy. Delete the copy afterwards.
3. Add a plain folder as a project with `POST /v1/core/projects` and no `workspaceId`. Each record a
   trigger starts makes a task, and a task in a git project makes a branch in this repository.
4. Save a one-step workflow with `POST /v1/p/workflows/defs`, publish it through
   `/defs/publications/prepare` and `/publish`, and open it in the window.
5. Choose **Add trigger…**, pick a suggestion, then **Review activation** and **Activate**.
6. Raise alerts with `POST /v1/core/plugins/acme-alerts/cli/raise` and a body of
   `{ "input": { "nodeId", "host", "load" } }`. That's the route `acorn plugin acme-alerts raise`
   calls. Read `GET /v1/p/workflows/workflows/triggers/<id>` for the trigger's matches.

A `dev:agent:ui run` script reaches the Node with `window.acorn.nodeFetch`. The project picker didn't
list the added project, so the window went to it with `history.pushState`.

## What the dialog offered

For the plain-folder project, **Start from a suggestion** listed four: **A high-load alert arrives**
from **Load alerts**, **A host's load goes above 4** from **Host load**, **A session needs you** from
**Managed agent sessions**, and **A run fails** from **Workflow runs**. The session has no GitHub,
GitLab, Bitbucket, Linear, or Rollbar account, so their suggestions had no source to come from. Each
of those passes `starterTriggerCheck` in its plugin's tests.

## The threshold walk

The trigger was the shipped suggestion **A host's load goes above 4**: **Host load**, load greater
than 4, **Starts matching**, checking every 5 minutes, with the dialog's default first check,
**Process current matches**. **Host load** is one record per host, holding its newest alert from the
feed. Raises for `web-3`, a host with no earlier alerts, about 20 seconds apart:

| Load | Raised, UTC | Runs the next check started for `web-3` |
| --- | --- | --- |
| 6.2 | 03:00:42 | 1, a second later |
| 6.4 | 03:01:01 | 0 |
| 5.8 | 03:01:20 | 0 |
| 2.1 | 03:01:39 | 0 |
| 6.0 | 03:01:58 | 1, a second later |

The walk passes. Each check ran about a second after its raise, because the raise route calls
`changed('hosts')` beside the feed's own signal. Both runs finished, each in its own task in the
scratch project, with the host's name in `issue`.

An earlier pass on `web-2` gave the same starts. Its first check also started `web-1`, which sat at
6.0 from before the trigger existed, because **Process current matches** starts a run for every
record that already matches. Both runs failed there: host records carried no display title, so
`issue` was empty. Each host record now carries its name as its title, and the `web-3` pass ran on
that build.

### The feed on its own

The first pass ran before **Host load** existed. It used the feed's suggestion, which was worded **A
host's load goes above 4** then and is **A high-load alert arrives** now: **Load alerts**, load
greater than 4, **Is new**. Raises for `web-1`, about 20 seconds apart:

| Load | Raised, UTC | Runs started by the next check |
| --- | --- | --- |
| 6.2 | 02:15:08 | 1, a second later |
| 6.4 | 02:15:33 | 1 |
| 5.8 | 02:15:52 | 1 |
| 2.1 | 02:16:17 | 0 |
| 6.0 | 02:16:36 | 1 |

That's what an event feed does. Each raise is a new event with its own ID, so it's a new record, and
**Starts matching** on the feed gives the same result, because no event ever stops matching. A
threshold that fires once until it clears needs a source of current state, which is why
`acme-alerts` serves **Host load** beside the feed.

## The run-fails walk

A second trigger on the same workflow came from **A run fails**. A workflow whose one step runs
`exit 1`, started by hand on one of the scratch tasks, failed at once, and the trigger started its run
within a second, through the Workflows plugin's `changed('runs')`.

That run failed too: "invalid input reference 'issue'". Workflow runs records carried no display
title, so the trigger named its match by the run's ID and left `issue` empty. The runs source now
gives each record the workflow's name as its title. After a rebuild the same walk named the match
"Failing check", filled `issue` with it, and the follow-up run finished. The trigger didn't start a
run for its own run.

## Checked against real services, read only

- **GitHub search.** Search's `status:` qualifier can't narrow the pull request search for `checks`.
  Over the open pull requests in `cli/cli`, `status:failure` returned 5 of the 6 whose combined check
  state was FAILURE, and the one it missed was 9 hours old. `status:success` returned 28 of 48.
  So `checks` takes `eq` and is compared after the read, with nothing sent to search.
- **Linear's schema.** Linear answers schema questions without a key. Every type, field, and filter
  the issue read uses exists: `Issue.team`, `Issue.labels(first:)`, `User.isMe`,
  `IssueFilter.labels.some.name`, `NullableUserFilter.isMe`, `TeamFilter.id` and `name`, and the
  `teams` and `issueLabels` queries with their filters.

## Not checked here

Each of these needs a real account and a change on a real service:

- **A Rollbar error seen twice** starting once, and again after it resolves and comes back.
  `errorSourceHandler.test.ts` reads the suggestion's predicate against a fake Rollbar.
- **A new pull request** starting a run within seconds of opening it, and within one cadence with the
  GitHub pane closed. `events.test.ts` checks the `changed()` call beside `pulls-changed` and
  `pr-synced` in GitHub, GitLab, and Bitbucket.
- **A pull request asks for your review**, when a teammate requests you, and again after you've
  reviewed.
- **A new Linear issue with a label** starting within one cadence. `issueRead.test.ts` covers the
  label, team, and assigned-to-you filters and options against a fake Linear.

**A session needs you** wasn't walked either, because it needs a live agent session to ask for
attention. Its suggestion passes the check in `sessionSource.test.ts`.
