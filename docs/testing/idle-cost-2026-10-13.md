# Idle cost check, October 13, 2026

This page records the counts behind [idle cost](../future/ui-performance/05-idle-cost.md). Every
number here comes from tests in jsdom, not from the real window. An agent-launched desktop window is
always hidden, and a hidden window never fires animation frames, so the replay's idle phases weren't
run. The counts say how often the code asks for work. They aren't CPU time or wakeups measured
from outside the renderer.

Three things did work that changed nothing on screen, and all three were changed. The frame-gap
sampler asked for a frame on every display frame of a focused idle window. The Changes rail marker
rewrote its map on every status poll. The Workflows pane button turned a loader while a workflow
agent waited for its owner.

## Machine and method

- Host: macOS on an Apple M2 Pro, at base `3d85f8c0e`.
- Frame requests: `responsiveness.test.tsx` replaces `requestAnimationFrame` with a 60 Hz clock the
  test drives and counts each request. Fake timers move the clock, `performance.now()`, and the
  telemetry flush. The focused, visible window has telemetry on and nothing else changing.
- Rail rows: `railMarker.test.tsx` (git plugin) mounts three dirty task rows, answers each status
  read with the same changes, and counts how often one row's markers run again over six polls. Six
  polls is an idle minute at the poll's 10-second interval.
- Base numbers come from running the same tests against the base file.

## Results

| What | Base | After |
| --- | ---: | ---: |
| Frame requests, first idle minute | 3,751 | about 125, all in the 2 seconds after arming |
| Frame requests, second idle minute | 3,750 | 0 |
| `ui.event_loop.delay` samples, two idle minutes | about 120 | about 120 |
| One rail row's marker reruns, six unchanged polls, three dirty tasks | 24 | 6 |

The six rail reruns that remain are the poll itself. A row reads the poll's revision so it asks for
each task's changes once per poll. The drawn markers don't change, because `RailTab` already holds
its markers while they say the same thing.

With telemetry off, the sampler requests no frames at all, before and after.

## What was checked and left alone

- Telemetry flush every 5 seconds, page facts every 30 seconds: telemetry work only, and only while
  collecting. Page facts skip a hidden window.
- Client schedules: task status every 10 seconds, Docker every 15 seconds, and pane availability,
  preview, and workflow runs every 120 seconds. Each already keeps its signal when the answer didn't
  change.
- Plugin chrome refresh: skipped while the window is hidden. A refetch that returns the same data
  keeps the query's data object, so nothing redraws.
- Tree worker heartbeat: a port message to each plugin worker, skipped while hidden. It changes
  nothing on screen.
- Agent usage, every 5 minutes while the indicator is mounted: each answer replaces the snapshot, so
  the two or three indicator rows draw again. The Node's answer carries a fresh `capturedAt` after its
  cache expires, so an equality check would rarely hold. It runs less than once an idle minute and
  wasn't changed.
- Tool card clock, once a minute while a tool body is open: the relative time it feeds can change on
  any tick.
- Workflow run clock, once a second while a step runs or waits at a gate: the elapsed text changes
  every second for the first hour.
- Node status frames: the broker sends one only when a Node's state or error changes.
- Endless animations: a session icon turns only while `working`, `cancelling`, or `reconnecting`. A
  tool card pulses only while its call runs, and the Node settles an unfinished call when its turn
  ends. A workflow run's gate shows as attention, not as running. The one exception was the
  Workflows pane button, which counted a `waiting` workflow agent as working.

## Real-window numbers still to take

A person at the machine needs to run these with the window visible and uncovered. Build both
renderers first:

```sh
git worktree add /tmp/idle-base 3d85f8c0e
cd /tmp/idle-base && pnpm install --frozen-lockfile && pnpm --filter @acorn/desktop build:renderer
cp -R /tmp/idle-base/apps/desktop/dist/client /tmp/idle-base-client
cd -
pnpm --filter @acorn/desktop build:renderer
cp -R apps/desktop/dist/client /tmp/idle-candidate-client
```

Then run the alternating comparison once with telemetry on and once with it off:

```sh
pnpm dev:agent -- --session idle-on --fixture streaming-replay --telemetry on --seed 1
pnpm dev:agent:ui -- --session idle-on replay-ab --base /tmp/idle-base-client --candidate /tmp/idle-candidate-client --fixture prose
pnpm dev:agent:ui -- --session idle-on stop
pnpm dev:agent -- --session idle-off --fixture streaming-replay --telemetry off --seed 1
pnpm dev:agent:ui -- --session idle-off replay-ab --base /tmp/idle-base-client --candidate /tmp/idle-candidate-client --fixture prose
pnpm dev:agent:ui -- --session idle-off stop
```

From each run report, record the renderer's CPU time and interrupt wakeups for `idle-focused`,
`idle-blurred`, and `hidden`, and the `ui.frame.gap` count for `streaming` and `idle-focused`. The
change passes if:

- With telemetry on, the candidate's `idle-focused` renderer wakeups and CPU fall within the spread
  of the two telemetry-off runs.
- The candidate's `ui.frame.gap` count during `streaming` stays close to the base's, and its
  `idle-focused` count is near zero.
- Scrolling still records `ui.frame.gap`. The replay has no scrolling phase, so scroll a long
  transcript by hand for a minute with telemetry on and the Sentry sink connected. Then find that
  minute's `ui.frame.gap` samples in Sentry.
