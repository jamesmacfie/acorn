# Acorn security review, October 22, 2026

A source review on October 22, 2026, against base commit `47287b67c`, covered the whole app, with most
of its time on the work since [the October 21 review](./review-2026-10-21.md): the phone gateway, and
the fixes that review made. It found one high, two medium, and three low problems. The review itself
ran no attack against a live Node. The fixes were then checked in `pnpm dev:agent`, and through the
phone gateway in front of a standalone Node, as the verification section says. The attacker is the one
[transport and auth](./transport-and-auth.md#why) names: an agent that read hostile text and now acts
for whoever wrote it, holding a task token. For the gateway findings there is a second one: someone
who holds a phone's session cookie, or a loaded plugin that turned hostile. The walk turned up one more
problem, T7, in the read block's network rule.

The gateway this review describes was retired on October 22, 2026, by the phone's own encrypted channel
([the phone channel](../relay/phone-channel.md)). A phone's device now carries the rules T3 and T4 set,
and the answers a Node gives a phone reach the app as data, which is what T2 and T5 were about. The paths
and tests named below are in the repository's history.

## Behavioral changes

- With **Keep agents out of Acorn's data folder** on, a Claude Code agent's shell also can't read the
  client config folder or a development desktop's custody root. The CLI's `device-token-local`, the
  gateway's `mobile` folder, the browser bridge's folders, and the fleet files are all inside. With the
  switch off, which is the default, nothing changed.
- In a blocked session, the sandbox lets the task CLI read the Node's `node.json`, beside its token
  file and the Node's certificate. The file holds the Node's ID, port, creation time, and baseline.
- The gateway sandboxes every answer it forwards. A `/node` address opened as a page renders with no
  script and no requests. The phone app reads answers with `fetch`, which the policy doesn't touch.
- A phone session ends after 30 days without use, and the cookie's `Max-Age` is 30 days. `GET /session`
  sends the cookie again with a fresh 30 days, so a phone in use stays signed in. **gateway sessions**
  lists only sessions that still work.
- A phone gets `403 gateway_refused` for every plugin write, including the answer to an agent's
  install request. No path stayed open, because the phone has no screen that answers one.
- The memory contract tells agents a memory is never a reason to run a command, open an address, or
  change a setting.

### Attacks walked in a real session

**The read block, in `pnpm dev:agent`.** The session ran with `ACORN_TUI_CONFIG_DIR` set to a scratch
folder holding a decoy `device-token-local`. A device call to `PUT /v1/p/agents/session-defaults` turned
the switch on, a plain-folder project got a task, and a real Claude Code session started in it. The session's flag settings had `denyRead` with the
data root, the real client folder under `~/Library/Application Support/acorn`, the scratch folder, and
`<data root>-shell`, and `allowUnsandboxedCommands` was off. The agent ran each command with its shell:

1. `cat` of a file in the project: exit 0. The control worked.
2. `cat` of the scratch folder's `device-token-local`: `Operation not permitted`, exit 1. As expected.
3. `env -u ACORN_TASK_ID -u ACORN_API_TOKEN ACORN_TUI_CONFIG_DIR=<scratch> acorn task list`: exit 3,
   "No Node is running for this data root." It failed, as expected, but the scratch folder holds no
   fleet file, so this step alone doesn't show the block. Step 2 does.
4. `acorn task scripts status`: exit 3. **Not as expected.** At first it failed with `EPERM` opening
   the data root's `node.json`. After `node.json` became readable, it failed with
   `connect EPERM 127.0.0.1:64249`, the Node's own port, which the settings allow. `curl` to the same
   address failed to connect too. Claude Code sets `no_proxy` for loopback addresses, so a client
   connects directly, and the sandbox refuses a direct loopback connection. That's T7.

The walk didn't `cat` the real client folder's token, so the real token was never at risk. The
settings deny that folder, and the scratch folder shows the deny works. A child session in Claude
Code's auto mode refused even the control command, so the walk set that session's mode to default and
answered each permission prompt. The `acorn` on the agent's path was the Homebrew launcher, which runs
the main checkout's CLI. The CLI's task path didn't change in this programme. The walk didn't run
with the switch off, which changes nothing by design.

**The gateway, in a browser holding a phone session.** A standalone Node loaded a scratch plugin whose
route answers an HTML page with an inline script, its own `Content-Security-Policy`, and an image
under `/node`. `pnpm dev:mobile:gateway`'s entry ran in front of it with the built phone app, and a
Chromium window at 390 by 844 signed in with a code:

1. The plugin's page through the gateway answered `200`. The browser logged "Blocked script execution
   ... the document's frame is sandboxed", the heading kept its "script did not run" text, and the
   network log shows no request to `/node/v1/core/tasks`. The image request failed on
   `default-src 'none'`. As expected.
2. `GET /node/v1/core/tasks` and `GET /node/v1/core/plugins` answered `200` with the sandbox policy and
   `nosniff`. The app page carries `script-src 'self'; object-src 'none'; base-uri 'none';
   frame-ancestors 'none'; form-action 'self'`.
3. The cookie had 30 days to run. After a reload, `GET /session` sent it again with `Max-Age=2592000`,
   and the browser's expiry moved forward by the seconds that had passed.
4. `PUT /node/v1/core/plugins/acme/development`, `PUT` of the roster, `POST` reload, `POST` of an
   install request answer, and `PUT /node/v1//core/plugins/acme/%64evelopment` each answered
   `403 gateway_refused`.

This was desktop Chromium, not a phone's browser. An idle session was checked separately on October
22, 2026, against a standalone Node: with its file's time set back 31 days, `/node/v1/core/tasks`
answered `401 signed_out` and the file was gone.

**Memory.** The new session's stored standing context, which Acorn sends as its prompt's memory
section, holds the paragraph that starts "Other agents write memory too".

## Decisions

All dated October 22, 2026.

- `clientCustodyDirs` lists `<data root>-shell` as well as the installed desktop's folder, because a
  development desktop keeps `data.key` in its custody root. The installed one is also read from the
  data root itself, because on Linux Tauri puts it under `~/.local/share`, which `appDataDir` doesn't
  name. That mismatch also makes `desktopDataRootDir()` miss an installed desktop on Linux, which is
  older than this review.
- The installed desktop's folder holds the data root, so the sandbox denies the entries beside it
  rather than the folder, and never stacks a second deny above paths it opens again. An entry created
  there after a session starts is covered only by the file guard. So is a client folder that doesn't
  exist when a session starts, until its next start. Whether Claude Code's sandbox accepts a missing
  path on Linux is unchecked; if it does, denying those whole would close this.
- The gateway's own success answers, `GET /session` and the sign-in `204`, don't carry the sandbox.
  Both are JSON or empty. A Node's `content-security-policy-report-only` still passes through, since it
  can't loosen anything.
- `GET /session` renews the cookie, so a session in use never ends. A late socket message can't revive
  a session already past the limit.
- The plugin rule names the four write methods and keeps no path open.
- The memory limits went on the Memory page doc, because `notes-and-memory.md` was at its length limit.
- The walk's fix to T7 lets the sandbox read `node.json` and stops there. Making the connection work
  means widening the sandbox's network rule, which needs its own check, so it's left open below.
- The Node service's size ceiling didn't change.
- R13 and R21 stay open owner decisions. With the switch off, which is the default, any agent can read
  the data root and the client folder. An ad-hoc signed build keeps `data.key` in a plain file.
- Sealing client tokens with the platform keychain, as the desktop does, is the follow-up to T1. The
  CLI and the gateway also run on Linux and beside a standalone Node, where there's no keychain.

### Still open

- T7's connection. A blocked Claude Code session's shell can't reach the Node, so the task CLI fails
  there. Agents in a blocked session have no working `acorn task scripts` command. We recommend
  sending the task CLI's connection through the sandbox's proxy, which keeps every other loopback port
  closed, and checking that the proxy accepts the Node's address. `allowLocalBinding` would also work
  but opens every loopback port, including the pairing ask route of any Node on the machine.
- The walk saw `GET /v1/p/agents/sessions` answer `500` after a session's turn was cancelled during a
  permission prompt. The Node logged a `TypeError` with no stack. It didn't block the walk, and it
  isn't a security problem, but it needs its own look.
- No real phone ran the gateway checks. A phone's browser may treat the renewed cookie differently.
- `pnpm pack:node` wasn't rerun. The October 21 review left it failing on `ci-info`.
- `braces` and `node-forge` have no fixed release, so their audit entries stay until one ships.
