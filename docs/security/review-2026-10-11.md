# Acorn security review, October 11, 2026

A source review on October 11, 2026, against base commit `fe2b5bec1`, found no route that a task token
or a remote device can misuse. It found four weaker spots and a drifted dependency graph. The
production audit had gone from zero advisories on October 1 to eight. A penetration review the same
day, against the same commit, tested what an agent can read from its working folder and added R9 to
R13. This page records each finding, the change that closed it, and the verification.

The node-forge advisory, [GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv), is
in RSA signature verification. Acorn uses node-forge only to create and sign its own TLS certificate
(`packages/node-core/src/server/transport/tls.ts`) and never verifies a signature with it. The
`auditConfig.ignoreGhsas` entry in `pnpm-workspace.yaml` carries that reason. Remove it and take the
release once a fixed node-forge ships.

## Behavioral changes

- A `.acorn/config.toml` layer or `.acorn/workflows/*.toml` file over 1 MiB, or one that isn't a
  regular file, produces one config error that names the file. The other layers and workflows load
  normally. Symlinks are still followed, so a linked personal config keeps working.
- A packaged desktop app ignores `ACORN_DEV_SERVER`. `pnpm dev` and `pnpm dev:agent` are unchanged.
- A reused `Idempotency-Key` with a different query string returns `409 idempotency_conflict`.
- The MCP review proxy answers `413` from the SDK transport for a message over 1 MiB, declared or
  streamed.

- A desktop-started Node refuses a start message without `keys`. Its data root holds
  `node-keys.sealed` and, after the first start, no `session.key` or `internal-token`, unless the key
  check failed, which keeps `session.key` and records `keys.check.failed`.
- A token signed before the upgrade fails from the first start. Reattached terminal sessions and
  restarted agent sessions get new token files.
- A standalone Node warns at boot that agents on it can read its keys, and refuses to mint a session
  key on a root the desktop has sealed.
- A task token gets `403` from `GET /v1/core/dashboards/history`.

## Decisions

- Read blocks for the data root (workstream 3) ship as an opt-in switch, off by default, after the
  owner chose it on October 11, 2026. Claude Code enforces a read block on shell commands only inside
  its sandbox, which also limits writes and network access, so turning it on for every session would
  break installs and SSH pushes. Runs in skip-permissions mode, with Claude Code 2.1.296 through
  `--settings` and through the Agent SDK's `settings` option that the ACP adapter passes on, confirmed
  that the sandbox refuses `cat` on a denied file and still allows the session's own file and
  worktree. Codex and contributed harnesses can't block a path. A commit review then found that the
  writable shared `.git` folder let an agent add a hook or an `fsmonitor` setting that the Node's
  unsandboxed git would run, and that hiding only top-level entries left the plugin databases beside
  a plugin's skill folder readable to Claude's file tools. A third review found that Linux skips
  wildcard write entries. The git control files, including the submodule folder, are now denied by
  concrete path, which a sandboxed commit from a linked worktree was checked against on macOS, and
  hiding descends to everything beside the session's own paths
  ([read block](../managed-agents/read-block.md)).
- A keychain marker for the key-swap case isn't planned. It only helps if deleting the keychain item
  needs the person's consent, which hasn't been checked on a packaged build, and a second item adds a
  keychain prompt after every re-signed update.
- The penetration review asked for the upgrade to re-sign live session token files with the new
  signing key. That needed the helper to accept an old signing key, and two commit reviews found
  ways for an agent to plant one and get a forged file re-signed. The Node already writes a new
  token file for each terminal session it reattaches and for each agent process it starts, so
  nothing re-signs. A session the Node doesn't reattach loses its token, as it would after any
  signing key rotation.
- An agent that deletes `node-keys.sealed` and plants its own `session.key` makes the next start look
  like an upgrade, and the Node then uses the agent's key. Any marker in the data root that could
  tell the two apart is one the agent can delete too.
- The Node's environment keeps variables from the environment the app was launched with, including
  secret-shaped ones. Every ancestor process already shows them, and a harness may pass one on with
  `envPassthrough`.

- CI doesn't fail on a new production advisory. The owner decided against it on October 11, 2026,
  because an upstream advisory would block unrelated merges. The audit stays a manual check.
- Mount coverage extends to the compiled plugins (R8). It can't reach a loaded plugin, which serves
  routes only through fetch handlers, so a third-party plugin's routes rely on the plugin's own checks.
  Making the host refuse task tokens by default on plugin routes would change the plugin contract and
  needs its own design.
